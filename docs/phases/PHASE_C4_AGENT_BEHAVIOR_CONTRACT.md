## 0. 本阶段做什么 / 不做什么

### 0.1 要解决的产品问题

旧隐含流程容易变成：

```text
用户故障 → Agent 查询 → 分析 → 自动创建工单
```

结果：Agent 退化为 **「智能工单机器人」**——分析只是建单前奏，工单成为默认终点。

V1 必须纠正为：

```text
用户提出故障
  → Agent 调查上下文（服务状态 / 运维知识 / 历史故障）
  → 生成分析回复
  → 按情况决定：
       1. 直接回答用户（默认）
       2. 用户确认后创建工单升级处理（escalation）
```

### 0.2 本文件职责

冻结 **Agent 产品行为契约**：定位、标准故障流程、Tool 使用规则、回复模板、E2E 验收 Case、与实现边界。

### 0.3 明确非目标（本文件与后续 C-4.x 实现均禁止自行加入）

```text
本设计阶段：不改任何业务代码
不修改 Graph 拓扑 / 节点拆分

不修改 HITL interrupt / resume 实现机制

不修改 Frontend / Go Backend
```

## 1. Agent 定位（终裁）

### 1.1 从什么调整到什么

| | 旧叙事（需纠正） | V1 终裁（本文） |
|---|---|---|
| 一句话 | AI 工单助手 | **AI 运维故障分析助手 + 工单闭环能力** |
| 默认终点 | 创建工单 | **可读、可依据的分析回复** |
| 工单角色 | 默认结果 | **escalation（升级处理）** |
| 核心价值 | 填单 / 落库 | **调查上下文、分析辅助决策、必要时闭环升级** |

### 1.2 一句话原则

> **先调查、再分析、默认可答；工单是升级，不是默认出口。**

### 1.3 价值分层

```text
L1 分析价值（主）
  - 聚合服务状态、知识库、历史故障
  - 给出有依据的判断与建议
  - 明确不确定边界，禁止幻觉

L2 闭环价值（辅）
  - 在需要人工跟进时，经 HITL 创建 / 更新工单
  - 工单承接「升级后的处理轨迹」，不替代分析
```

### 1.4 非定位（禁止宣传 / 禁止行为）

```text
不是自动建单机器人
不是无依据的根因断言引擎
不是 Prometheus / 真实日志平台
不是 Permission / AccessRequest 助手（Legacy）
不是「查完就建单」的流水线
```

## 2. 标准故障处理流程（产品编排）

> 以下是 **Prompt 约束的推荐编排**，不是新的独立 Graph 节点。  
> 实现仍走现有 ReAct；不得为此新增节点类型。

### 2.1 主路径

```text
User Query
    ↓
Intent Understanding
    ↓
Context Gathering
    ├── get_service_status / list_services
    ├── search_knowledge
    └── search_tickets
    ↓
Generate Analysis Response
    ↓
Decision
    ├── 无需人工 → 直接回复（默认）
    └── 需要人工 → HITL + create_ticket（升级）
```

### 2.2 各阶段职责

| 阶段 | 职责 | 允许的 Tool | 禁止 |
|------|------|-------------|------|
| Intent Understanding | 识别是否故障咨询 / 是否明确要求建单 / 是否缺关键实体 | 可读 `get_current_user`；必要时 `list_services` 消歧 | 直接 `create_ticket` |
| Context Gathering | 收集可引用证据 | 读工具（见 §3） | 写工具；编造证据 |
| Generate Analysis Response | 按 §4 模板组织回复 | 无（基于已有 Tool 结果） | 声称已定位且无依据 |
| Decision | 直接答 或 提议升级 | 升级时才进入写工具 + HITL | 静默建单；无分析建单 |

### 2.3 Context Gathering 最低期望（故障类意图）

对 **可定位到服务或明确故障现象** 的查询，Agent 应尽量完成三类调查（顺序可按缺参调整，但不得整类跳过却断言结论）：

1. **服务状态**：`get_service_status`（或先 `list_services` 再取状态）  
2. **运维知识**：`search_knowledge`  
3. **历史故障**：`search_tickets`（可按关键词 / `service_id`）

可选辅助：

- `get_current_user`：明确「谁在报障」  
- `get_ticket`：用户点名某张单时再拉详情  

### 2.4 Decision 规则（何时升级）

**直接回复（无需人工）——默认：**

```text
用户只是咨询 / 排查 / 询问现状
上下文已足够给出建议或「依据不足」说明
用户未要求创建工单，且场景不强制升级
```

**HITL + create_ticket（需要人工）——升级：**

```text
用户明确要求提交 / 创建工单 / 升级处理
或 Agent 判断需要人工跟进，并先给出分析，再征求确认
或用户在分析回复后肯定回答「是，请升级 / 帮我建单」
```

**update_ticket：**

```text
仅在已有工单语境且用户意图为更新状态 / analysis 等写操作时
同样必须 HITL；不得用 update 代替分析
```

### 2.5 与 Phase A Demo 剧本的关系

Phase A §8 仍可作为「升级闭环」演示路径，但产品默认解释改为：

```text
张明报障
  → 先完成三类调查 + 分析回复
  → 仅当张明确认升级（或首轮就明确要求建单）
  → HITL → create_ticket
  → 王运维处理闭环
```

禁止把 Demo 讲成「一问故障就自动弹出建单」。

## 3. Tool 使用规则

### 3.1 读工具 — 自动执行

| Tool | 用途 |
|------|------|
| `get_current_user` | 当前用户身份上下文 |
| `list_services` | 服务目录 / 消歧 |
| `get_service_status` | 模拟健康状态与 `health_summary` |
| `search_tickets` | 历史故障 SQL 检索 |
| `get_ticket` | 单票详情 |
| `search_knowledge` | 运维知识（Milvus Retriever） |

规则：

```text
读工具：自动执行，不走 HITL
故障类意图：优先完成 §2.3 三类调查再下结论
只引用 Tool 返回内容；hits=[] / 无匹配时必须说明依据不足
```

### 3.2 写工具 — 必须 HITL

| Tool | 用途 | HITL |
|------|------|------|
| `create_ticket` | 升级处理：创建工单 | **必须** approve/reject |
| `update_ticket` | 更新已有工单 | **必须** approve/reject |

规则：

```text
写工具：禁止静默执行
create_ticket 前必须已有（或同轮即将给出的）分析结论，不得「空分析建单」
用户未确认前，只能提议升级，不能假装已建单
reject 后：保留分析价值，不强制再次建单
```

### 3.3 硬性禁止

```text
禁止：没有分析就创建工单
禁止：编造日志、指标、根因、ticket_no、健康状态、知识步骤
禁止：在无 Tool 依据时声称「已经定位问题 / 已确认根因」
禁止：把 search_knowledge 未命中写成公司官方结论
禁止：把其他用户不可见的历史单内容泄露给 Employee（遵守 Backend 可见性）
禁止：为「看起来完整」而跳过调查直接给根因故事
禁止：Permission / AccessRequest 类 Tool 或主流程（Legacy）
```

### 3.4 不确定性话术（契约级）

当证据不足时，允许且应当：

```text
说明当前无法确认根因
列出已查到的事实（若有）与未查到的项
给出保守建议（重试、观察、联系值班、或是否升级）
询问用户是否需要升级处理
```

不允许用常识或训练语料补「公司内部已发生的事实」。

## 4. 回复模板（V1 推荐结构）

故障分析类回复应覆盖下列板块（标题可微调，语义不可缺）：

```text
问题判断：
  （用户现象的一句话归纳；可标注置信度：较有把握 / 依据有限）

当前状态：
  （来自 get_service_status / list_services 的摘要；无则写「未查到服务状态」）

知识依据：
  （来自 search_knowledge 的可追溯要点；无命中写「知识库暂无直接命中」）

历史参考：
  （来自 search_tickets 的可见历史；无则写「未见同类可见历史工单」）

建议操作：
  （可执行、保守、与依据一致；区分「用户可自助」与「需运维」）

是否需要升级处理？
  （默认询问；若用户已明确要求建单，则说明将进入确认后创建工单）
```

### 4.1 模板使用规则

```text
直接回答路径：完整输出模板，不以建单结尾为成功
升级路径：先满足模板中的分析信息，再进入 HITL create_ticket
Support 处理已有单：可聚焦 analysis / 状态建议，仍禁止无依据断言
短追问（如「那个服务现在怎样」）：可只答相关板块，但不得伪造其他板块事实
```

### 4.2 示例骨架（非实现文案冻结）

```text
问题判断：Checkout 相关接口疑似 5xx / 支付链路异常（依据：用户描述 + 服务状态）。

当前状态：CHECKOUT_API = DEGRADED；摘要：……

知识依据：命中《……》中关于 5xx 排查的步骤：……

历史参考：可见历史单 OPS-V1-2001：……

建议操作：1）…… 2）……

是否需要升级处理？如需人工跟进，请回复确认后我再创建工单。
```

## 5. E2E 验收 Case（行为契约）

> 验收看 **行为与结果**，不要求本阶段改代码。  
> C-4.1 实现后按本表手测；未通过不得宣称 C-4 完成。

### Case A — 普通故障咨询（默认不建单）

| 项 | 内容 |
|----|------|
| 输入 | `checkout接口502` |
| 角色 | Employee（张明） |
| 期望调查 | 调用（至少意图覆盖）`get_service_status` 或经 `list_services` 定位后取状态；`search_knowledge`；`search_tickets` |
| 期望回复 | 含 §4 结构的分析；引用 Tool 结果；询问是否升级 |
| 期望写操作 | **不**调用 `create_ticket` / `update_ticket`；无 HITL 写确认 |
| 失败判定 | 未调查就给根因；或自动建单；或编造日志/指标 |

### Case B — 明确要求人工处理（分析后升级）

| 项 | 内容 |
|----|------|
| 输入 | `checkout接口502，帮我提交工单` |
| 角色 | Employee（张明） |
| 期望调查 | 同 Case A，先完成上下文调查 |
| 期望回复 | 先给分析（§4），再进入升级 |
| 期望写操作 | **HITL** → 用户 approve 后 `create_ticket`；reject 则不建单且分析仍可用 |
| 失败判定 | 无分析直接 interrupt 建单；或跳过 HITL；或建单成功却无 `service_id`/分析摘要等基本信息 |

### Case C — 知识不足（拒幻觉）

| 项 | 内容 |
|----|------|
| 输入 | `未知系统异常`（或明显无法映射到已知服务 / 知识的模糊报障） |
| 角色 | Employee |
| 期望行为 | 尝试合理消歧或检索后，明确说明 **无法确认**；知识/历史无命中须直说 |
| 期望回复 | 不编造根因、日志、指标、内部系统名「已确认故障」；可建议补充信息或询问是否升级 |
| 期望写操作 | **默认不建单**；仅当用户明确要求升级时才走 HITL |
| 失败判定 | 虚构排查过程；声称已定位；或为「有交代」强行建单 |

### Case D —（建议）用户先咨询后确认升级

| 项 | 内容 |
|----|------|
| 输入轮次 | ① `checkout接口502` → ② `是，请升级处理` / `帮我建单` |
| 期望 | ① 同 Case A；② 基于已有分析进入 HITL + `create_ticket`，不重复编造新根因 |
| 失败判定 | ② 忽略前文分析空单创建；或 ① 已偷偷建单 |

### Case E —（建议）写操作拒绝后仍保留分析

| 项 | 内容 |
|----|------|
| 过程 | 用户要求建单 → HITL reject |
| 期望 | 不落库；向用户说明已取消升级；分析结论与建议仍可阅读 |
| 失败判定 | reject 后仍显示已创建；或清空分析只剩「已取消」 |

## 8. 一句话收束

> **OpsPilot V1 Agent 先当运维分析助手，再提供工单升级闭环；工单是 HITL 确认后的 escalation，不是对话的默认产物。**
