# 信息系统访问与权限管理规范

## 1. 使用场景

申请或咨询公司托管资源的访问级别时使用本文：

| resource_type | 含义 |
|---------------|------|
| `GITLAB` | 代码仓库 |
| `DATABASE` | 业务/分析库等 |
| `DEV_ENV` | 开发 / 联调 / 预发类环境 |

权限级别：`READ` | `DEVELOPER` | `ADMIN`。原则：能低不高；一事一申请（三类互不替代）。

VPN、装软件、改密码 → **不是**本文对象（走工单/对应 howto）。

## 2. 判断流程

1. 只问「要不要审批 / 和工单有啥区别」？→ **answer**
2. 确认 `resource_type`、`resource_name`、`permission_level`、`reason` 齐全？  
   - 缺参 → 先追问，再 **permission**  
   - 齐全 → `create_permission`
3. 下列情形即使已提交申请，也必须明确 **human**（不得暗示自动通过）：  
   - 任意 `ADMIN`  
   - 生产环境数据库访问  
   - 要求跳过 Approval  
   - 代人申请且用途不清  
   - 申请人与资源明显不符 / 制度未覆盖的新平台
4. 查询「我的权限申请」→ 调业务查询 Tool，不编造审批结果

## 3. 边界条件

- 群聊/口头「同意」**不能**代替系统 Approval；未获批不得访问。
- 禁止 Ticket「顺便开通」三类资源。
- 禁止共享个人账号；禁止申请材料含私人令牌/连接串明文。
- `resource_name` 须具体（仓库路径/库名/环境名），禁止只写「生产」「所有仓库」。
- 知识说明「可以申请某级别」≠ 已开通。

## 4. 示例问题

1. 「只读库要走工单还是权限？」→ **answer**：走 **permission**（DATABASE + 通常 READ）
2. 「GitLab 和开发环境是一回事吗？」→ **answer**：不是，需分别申请
3. 「申请 OpsPilot 仓库 Developer」→ **permission**
4. 「生产库给我 Admin，群里说过了」→ **human**（可引导仍提交 permission，不得自动通过）
5. 「我的权限申请批了没？」→ 查列表 Tool，不以本文断言
